  type: feedback

**Classify failures by a stable code, never by matching substrings in a message.** This applies to any dependency's error surface, not just SQLite's.
**Why:** `:cri` already documents the rule (`ErrorTranslation.kt`: "descriptions are free-form and change between releases"), and `:store` was called out in review for breaking it — a `SQLITE_BUSY` whose wording drifts in a driver bump silently becomes a permanent failure and drops a server from the reconcile queue until the resync. Review checks the modules against each other, so a pattern one module rejected is expected to stay rejected in the others.
**How to apply:** naming a vendor type (`org.sqlite.SQLiteErrorCode`) inside an `internal` package backed by an `implementation` dependency is fine and was explicitly blessed — the boundary is the public interface, not the import list. Pair it with a test whose fixture *messages disagree with their codes*, so a reversion to substring matching fails rather than passes.

**Every new test gets proved against a broken implementation before it ships — name the test and the mutation in the report.**
**Why:** review asked for a deterministic test "or say so rather than shipping a flaky one", and the user has since asked for this on plain non-concurrent tests too ("prove each new test bites by breaking the behaviour it covers"). A test that passes on both the fixed and the broken code is documentation, not a guard.
This extends to *documented* claims about what a future change will break. Writing "bumping X fails these tests" without running it produced a wrong sentence on the first draft: bumping `PropertyDocument.ENCODING_VERSION` to 2 fails seven `MigrationTest` cases on V3's encoding refusal, but the one fixture that looks most relevant (the unreadable-encoding row, pinned to 2) keeps *passing* while silently ceasing to test what its name says. Only the mutation surfaced that, and it was the most useful half of the note.
**How to apply:** back up the file, mutate exactly the behaviour under test (`if (x)` → `if (false)` is usually enough), run, restore. Aim for a mutation only the *new* test catches, so the report can say which one bit. For a concurrency defect the same procedure applies but the claim is a measured hit rate over several runs, not a single failure — shape the window wide (large buffers, readers looping, a head start before the destructive call) instead of hoping for a lucky interleaving.
**When the claim is about a field nobody has written yet, the mutation has to add the field for real.** Audit 32 asked for a guard on "add a fourth field to `BackendDrainSpec` and the rebuild silently defaults it". The tempting cheap mutation — drop one of the three *existing* fields from the rebuild — is caught by the older tests too, so it proves nothing about the new one. Adding a genuine fourth field (record + its reader + the `*-full.yaml` example, three edits) and running the rebuild both ways gave the uniqueness result instead: one failing case, and it was the new one. Parametrise the driver by module (`MODULE=store`) and the same mutation answers "is the sibling shape in my module guarded too" in one more run.

**Prefer a guard that leaves the shipped code shape untouched over one that reformats it.**
**Why:** hoisting version 3's duplicate-key check above its `when` instead of nesting it inside a branch kept the migration's decision table byte-identical in the diff, in a file whose own rules say it may never be edited again. `spotlessApply` expands sibling branches into blocks the moment one becomes a block, so an in-branch guard churns lines that carry signed-off semantics.
**How to apply:** fire the guard on exactly the condition that would have failed, then leave the original expression alone.

**Raise a change to shipped-migration behaviour as a decision; do not make the call unilaterally. Confirmed.**
**Why:** the report flagged that adding an encoding guard to V2 would turn a migration that already succeeded on real disks into one that refuses, and asked for a decision instead of shipping a fix. The user upheld it verbatim ("your reasoning held") and chose *document the gap, do not retrofit it* — the never-edit-a-shipped-migration rule outranks closing a hole that is theoretical while only encoding 1 has ever been written. The same shape recurs: a gap in already-shipped code gets recorded plus a rule stopping it propagating to new code, rather than closed.
**How to apply:** when a fix would change what a shipped migration does on an existing disk, write it up as a decision with the tradeoff and let the user pick. Pair "leave it" with a note on the old code saying why it is deliberately not being fixed *and* a line in the procedure requiring the guard on new code, so the exemption is grandfathered rather than precedent.

**A fix that changes what `:core` or `:api` see is reported, not reached into — the user routes those modules separately.**
**Why:** said explicitly on the ninth audit's fix (2026-07-31): "If your change alters what `:core` or `:api` see, say so clearly rather than reaching into them — I will route those." Combined with the hard requirement that `./gradlew build` stays green, this means the change must be source-compatible with both modules *and their test fakes* — see [[store-design-decisions]] on frozen signatures.
**How to apply:** design additively, then in the report list per module what changes behaviourally without any edit, and what each module would have to adopt to get the full benefit. Do not leave the build red expecting someone else to finish it.

**When an audit hands over a reading of the code, reproduce it before fixing it — the user asks for this explicitly.**
**Why:** the tenth audit's brief said "the auditor asked for a two-minute confirmation with a raw-SQL NULL insert rather than accepting its reading. Do that first... if it turns out SQLite rejects it, say so and stop." The probe confirmed it (`NullPointerException: getString(...) must not be null`), and the same habit then paid off twice more: probing the *fix* showed the documented `NOT NULL` rebuild silently empties `server_status`, which changed the design.
**How to apply:** write a throwaway test that prints what happens, run it, delete it. Probe the proposed remedy as well as the reported defect — "does the prescribed fix do what it claims on this schema" is where the surprises are. See [[store-design-decisions]] on the cascade.

**A migration that copies old keys then writes new ones must guard the duplicate on every key it writes. Found twice now.**
**Why:** `DocumentWriter.put` is `require(fields.put(key, value) == null)`, so a repeat throws `IllegalArgumentException` — not a `StoreException`, not wrapped by `Migrations.applyOne`, and therefore a type `:core` cannot classify escaping out of `EmbeddedStore.open`. V3 hit it (both-keys row) and V5 hit it again in a nastier form: the guard named `drain.blocked.reason` while the rewrite wrote four `drain.blocked.*` keys, so a row carrying only `message`, `since` or `observations` slipped through into exactly the crash the guard existed to prevent.
**How to apply:** guard on the shared prefix (`document.keys().any { it.startsWith(...) }`), never a representative key, so a field added to the record later is covered by construction. Test it with a parametrised case *per key*, so the fixture set cannot drift from what the guard checks. The rule now lives in the "Adding version N" checklist in `Migrations.kt`, which is the thing to update when a pattern recurs rather than only fixing the instance.

**A fixture that names a real enum member to mean "unknown" rots the day that member ships.**
**Why:** `CorruptStoreTest`'s "a kind this build does not know is refused" mutated a row to `kind = 'VelocityProxy'`. When `:store` learned that kind (2026-08-05) the row decoded, the test failed, and had it been written more loosely it would have silently stopped testing anything. `ServerKind` is meant to grow, so no real member can stand in for an unknown one.
**How to apply:** spell "unknown" as a value no build has ever written (`BedrockServer`), and say in a comment why it is not a real member. Same reasoning as the frozen literals in migrations: the fixture has to keep asking the same question after the live types move.

**Near a branch sign-off, report defects instead of opportunistically fixing them.**
**Why:** the user wants to route work deliberately when a branch is about to be signed; an unplanned fix landing inside a docs-only pass muddies what is being signed off. Said explicitly during the 2026-07-28 documentation pass.
**How to apply:** in a scoped pass (docs-only, comments-only), if something turns out to be a real defect, finish the scoped work and surface the defect in the report. Keep the diff to the stated scope — a `git diff` filtered to non-comment lines returning empty is a cheap way to prove it.

**A round-trip fixture that encodes a state no build could write turns into a false assertion the day a read-side rule lands. Check the fixtures before writing the rule.**
**Why:** `Fixtures.fullDrain` built a `STOPPING` drain with `stopDispatchedAt = null` — a pair the orchestrator never produces, since `STOPPING` is only reached after a stop returned. `StatusReconstruction` made `every drain state round-trips` fail in *both* implementations, which was the right signal, but the fix is to correct the fixture (stamp it only in `STOPPING`, at an instant distinct from the one the rule synthesises, so a dropped key is still visible) rather than to weaken the round-trip claim. Deleting or narrowing the test would have been the forbidden move.
**How to apply:** before adding any read-side rule, grep the shared fixtures for records that violate the invariant the rule assumes. Two failing tests on the first run is confirmation the rule reaches both implementations — read it as evidence, not as a problem.

**Deviating from a reviewer's prescribed mechanism is fine if the mechanism does not close the hole — say why in the code.**
**Why:** the review asked for `@Volatile` plus a compare-and-set on `SecretValue.destroyed`. A CAS makes the wipe happen once but does not stop a `use` that already passed the check from copying a half-wiped buffer, so the fix took a lock for the copy/wipe critical section and kept `@Volatile` for the lock-free flag read.

See [[store-design-decisions]] for the module's other load-bearing choices.
